Automatic Data Sync

Sending your office's Contacts and Pipeline to the GREA Portal without uploading files by hand

Today you export a file from your CRM and upload it through the portal. This guide covers the alternative: having that same file sent automatically on a schedule, so the portal stays current without anyone remembering to do it.

You don't need a developer. If your office produces a spreadsheet today, the whole setup is one command in a scheduled task. If your office has technical people or a system like Salesforce, they can connect more directly — the same instructions apply either way.

Nothing changes about your file. The API accepts exactly the same CSV you already prepare for manual upload — same columns, same rules. If a file imports through the portal today, it imports through the API too.

Before you start

Ask Jeff for your office's API key. It looks like this:

grea_live_7Kd2mQ...
Treat the key like a password. It lets whoever holds it replace your office's data. Don't email it around, don't put it in a shared document, and don't paste it into a message thread. Store it the way you'd store a password. If it's ever exposed, tell Jeff and he'll cancel it and issue a new one — same as a password reset. A key only ever works for your office; it cannot touch another office's data.

The one thing to understand first

Every sync replaces all of your office's data for that type. Each time you send contacts, the portal deletes your existing contacts and loads the file you sent. It does not add to what's there.

This means: always send your complete current list, never just the new or changed records. If you send 10 contacts, you will have 10 contacts.

This is deliberate. On an automatic schedule, an "add to what's there" mode would duplicate your entire list every single run.

Contacts and Pipeline are separate. Sending contacts never affects your pipeline, and vice versa.

Step 1 — Check your key works

Start here. This touches no data at all; it just confirms the key is valid and tells you which office it belongs to.

Windows (PowerShell):

curl.exe -H "Authorization: Bearer YOUR_KEY_HERE" `
  https://grea-portal.vercel.app/api/v1/whoami

Mac or Linux:

curl -H "Authorization: Bearer YOUR_KEY_HERE" \
  https://grea-portal.vercel.app/api/v1/whoami

You should get back:

{"ok":true,"office":"PHL","keyLabel":"Weekly HubSpot sync"}

If the office code shown isn't yours, stop and tell Jeff.

Step 2 — Test your file without changing anything

Add ?dry_run=1 and the portal will check your entire file and report exactly what would happen — without writing anything. Use this until the result looks right.

Windows (PowerShell):

curl.exe -X POST `
  -H "Authorization: Bearer YOUR_KEY_HERE" `
  -H "Content-Type: text/csv" `
  --data-binary "@C:\path\to\contacts.csv" `
  "https://grea-portal.vercel.app/api/v1/import/contacts?dry_run=1"

Mac or Linux:

curl -X POST \
  -H "Authorization: Bearer YOUR_KEY_HERE" \
  -H "Content-Type: text/csv" \
  --data-binary @contacts.csv \
  "https://grea-portal.vercel.app/api/v1/import/contacts?dry_run=1"

For pipeline data, change contacts to deals in the web address.

Step 3 — Go live

Exactly the same command with ?dry_run=1 removed. That's the only difference.

curl -X POST \
  -H "Authorization: Bearer YOUR_KEY_HERE" \
  -H "Content-Type: text/csv" \
  --data-binary @contacts.csv \
  https://grea-portal.vercel.app/api/v1/import/contacts

Reading the result

{
  "ok": true,
  "dryRun": false,
  "office": "PHL",
  "entity": "contacts",
  "received": 352,     // rows found in your file
  "imported": 350,     // rows now in the portal
  "deleted": 340,      // previous rows replaced
  "skipped": 2,        // rows with problems (listed below)
  "skippedRows": [
    { "row": 17, "errors": ["contact_name is required"] }
  ],
  "warnings": [ "..." ]
}
FieldMeaning
importedHow many records your office now has. This is the number to watch.
skippedRows that couldn't be imported. Each one is listed with the reason and its row number.
deletedHow many previous records were replaced. Expected — see the replace note above.
warningsThings worth knowing that didn't stop the import — an unrecognised broker email, contact details removed, and so on.
A few skipped rows is normal and safe. Good rows still import; only the problem rows are left out, and each is named so you can fix it at source. What you should never ignore is "ok": false — that means nothing was written at all.

Broker Email is what links a record to a broker's portal account, so it needs to match the email they log in with. If it doesn't match a registered user the record still imports, showing the Broker Name as plain text, and links automatically on a later sync once that person is set up.

Contact phone numbers and email addresses

Under the current network-wide guidelines, offices share a contact's name and company only. The portal enforces this automatically: if your file happens to contain contact phone numbers or email addresses, they are removed before anything is saved, and the response tells you how many were removed.

You don't need to strip them out of your export. Nothing is rejected because of them.

Running it automatically

Windows — Task Scheduler

  1. Save your command into a .bat file, with your CRM export saved to a fixed path each time.
  2. Open Task Scheduler → Create Basic Task.
  3. Set it to run weekly on your chosen day.
  4. Point the action at your .bat file.

Mac or Linux — cron

# Every Monday at 6am
0 6 * * 1 /path/to/sync-contacts.sh

No scripting at all

Tools like Zapier or Make can send a scheduled request without any code. Point them at the same web address, with the same Authorization header and your file as the body.

Salesforce and similar systems

A scheduled export feeding the same command works well. If you have a developer, they can post JSON instead of CSV — see the note at the end.

Checking that a sync actually ran

curl -H "Authorization: Bearer YOUR_KEY_HERE" \
  https://grea-portal.vercel.app/api/v1/imports

Returns your recent syncs with dates and row counts, so you can confirm last night's run landed without logging in.

When something goes wrong

You seeWhat it meansWhat to do
401The key is missing, mistyped, or wrongCheck the Authorization header, then ask Jeff for a new key
403The key was cancelledAsk Jeff to issue a new one
413File is over 5 MB or 10,000 rowsSplit it, or narrow the export
415Wrong Content-TypeUse text/csv
422A required column is missing, or no row was usableRead the error text; nothing was written
429Too many syncs in one hourWait. The limit is 10 real syncs an hour, and 50 dry runs
Your data is never left half-updated. If a file is rejected — a missing column, or no usable rows — the portal writes nothing and your existing data stays exactly as it was. A broken export can't wipe your office.

For developers

Instead of CSV, you can send Content-Type: application/json with a body of {"rows": [ ... ]}, using the template's underlying field names (contact_name, account_name, broker_email, and so on). List fields accept either a JSON array or a semicolon-separated string; Confidential accepts a real boolean. Validation is identical to the CSV path.
