Sending Data to the GREA Portal

A standard web API that any system can send your office's Contacts and Pipeline to, automatically

The portal accepts data over a normal HTTP API. Any system that can make a web request can send to it — a CRM, an in-house database, a script, an automation tool. Nothing is specific to one product, and the portal never connects to or logs into your systems; your side sends, we receive.

Today someone exports a file and uploads it by hand. This replaces that with something that runs on its own.

Two ways to send

Both go to the same endpoint and are validated identically. Pick whichever suits what you already have.

Send JSON directlySend a CSV file
Good when Your system can make an outbound web request — most CRMs and anything custom-built You already produce an export file and don't have a developer
Needs Someone who can configure an API call in your system A scheduled task running one command
Content-Type application/json text/csv
There is no file involved in the JSON path. Your system builds the records and posts them straight to the portal. The CSV option exists for offices without a developer — it is a convenience, not the intended shape.

Setting this up is a technical task — not difficult for someone who does that kind of work, but not something to expect of yourself unless you're comfortable with it. The good news is it's a one-time job: once running, nothing is needed from you week to week.

Staying with manual uploads is a perfectly good choice. The upload button in My Office isn't going away, and an office that keeps using it is not doing anything wrong. Automate when it's worth the setup effort to you, not because it's expected.

The one thing to understand first

Every call replaces all of your office's data for that type. The portal deletes your existing contacts and stores what you sent in their place. Unlike the manual upload in the portal, there is no "add to what's already there" option here.

This means: always send your complete current list, never just the new or changed records. If you send 10 contacts, you will have 10 contacts.

This is deliberate. On an automatic schedule, an "add to what's there" mode would duplicate your entire list on every run.

So this is a whole-list interface, not a record-by-record one. Don't wire it to fire when a single record changes in your system — have it send the full current list on a schedule.

Contacts and Pipeline are separate. Sending contacts never affects your pipeline, and vice versa.

Before you start

Ask Jeff for your office's API key. It looks like this:

Treat the key like a password. It lets whoever holds it replace your office's data. Don't email it around, don't put it in a shared document, and don't paste it into a message thread. From here on, this is for whoever is doing the setup. As the office admin you don't need to follow the technical detail below — though "Reading the result" and "The fields" are worth a look, since those are what you'll see week to week.

The API

Base address: https://grea-portal.vercel.app. Every request carries the key in a header, and every response is JSON.

Authorization: Bearer grea_live_...
MethodPathWhat it does
GET/api/v1/whoamiConfirms the key works and names the office. Touches no data.
POST/api/v1/import/contactsReplaces the office's contacts
POST/api/v1/import/dealsReplaces the office's pipeline
GET/api/v1/importsRecent runs, with dates and row counts

Add ?dry_run=1 to either POST and the portal validates everything and reports exactly what would happen, without writing anything. Build against dry-run first; switch it off only when the numbers look right.

Sending JSON

POST to the endpoint with Content-Type: application/json and a body shaped like this:

{
  "rows": [
    {
      "contact_name": "Jane Doe",
      "account_name": "Acme Holdings",
      "broker_email": "sramos@grea.com",
      "broker_name": "Steffan Ramos",
      "sectors": ["Student Housing", "Multifamily"],
      "relationship_status": "Active",
      "last_contact_date": "2026-08-14",
      "is_confidential": false
    }
  ]
}

Notes on the format:

  • List fields (sectors, tags) accept a real JSON array or a semicolon-separated string.
  • is_confidential accepts a real boolean.
  • Dates are YYYY-MM-DD. A timestamp is accepted; the time is ignored.
  • Unknown keys are ignored, and omitted optional fields are treated as blank — so you can send a superset of what we use.

Deals use the same envelope with the pipeline fields. Both are listed under "The fields" below.

Sending a CSV instead

If you'd rather send the export file you already produce, POST it with Content-Type: text/csv. It's the same template as the manual upload — same headers, same rules. Whoever sets this up doesn't need to understand your CRM or reshape anything.

Check the key first (Mac or Linux; on Windows PowerShell use curl.exe and a backtick instead of the backslash):

curl -H "Authorization: Bearer YOUR_KEY_HERE" \
  https://grea-portal.vercel.app/api/v1/whoami

You should get back:

{"ok":true,"office":"PHL","keyLabel":"Weekly export"}

If the office code shown isn't yours, stop and tell Jeff.

Then test the file, writing nothing:

curl -X POST \
  -H "Authorization: Bearer YOUR_KEY_HERE" \
  -H "Content-Type: text/csv" \
  --data-binary @contacts.csv \
  "https://grea-portal.vercel.app/api/v1/import/contacts?dry_run=1"

Then go live — the identical command with ?dry_run=1 removed. That is the only difference. For pipeline data, change contacts to deals.

Reading the result

Every call returns the same report, whichever format you sent.

{
  "ok": true,
  "dryRun": false,
  "office": "PHL",
  "entity": "contacts",
  "received": 352,     // records you sent
  "imported": 350,     // records now in the portal
  "deleted": 340,      // previous records replaced
  "skipped": 2,        // records with problems (listed below)
  "skippedRows": [
    { "row": 17, "errors": ["contact_name is required"] }
  ],
  "warnings": [ "..." ]
}
FieldMeaning
importedHow many records your office now has. This is the number to watch.
skippedRecords that couldn't be imported. Each is listed with the reason and its position.
deletedHow many previous records were replaced. Expected — see the replace note above.
warningsThings worth knowing that didn't stop the run — an unrecognised broker email, contact details removed, and so on.
A few skipped records is normal and safe. Good records still import; only the problem ones are left out, and each is named so you can fix it at source. What you should never ignore is "ok": false — that means nothing was written at all.

Whatever you build, make sure a human sees at least the summary line. A scheduled job that fails silently is worse than no job.

Broker Email is what links a record to a broker's portal account, so it needs to match the email they log in with. If it doesn't match a registered user the record still imports, showing the Broker Name as plain text, and links automatically on a later run once that person is set up.

Contact phone numbers and email addresses

Under the current network-wide guidelines, offices share a contact's name and company only. The portal enforces this automatically: if what you send contains contact phone numbers or email addresses, they are removed before anything is saved, and the response reports how many.

You don't need to strip them out first. Nothing is rejected because of them.

Running it on a schedule

How you schedule it depends on what's sending.

If you haveTypical approach
A CRM with outbound calls or automationA scheduled job in the CRM that gathers the full list and posts it as JSON
A developer and any systemA small script on whatever runs your other scheduled work
No developerZapier, Make or similar can send a scheduled request without programming. Still needs configuring once, but avoids scripts
Only an export fileWindows Task Scheduler or cron running the curl command above, against an export saved to a fixed path
# cron — every Monday at 6am
0 6 * * 1 /path/to/send-contacts.sh

Weekly suits most offices. There's no benefit to running it more often than your data actually changes.

Checking that a run happened

curl -H "Authorization: Bearer YOUR_KEY_HERE" \
  https://grea-portal.vercel.app/api/v1/imports

Returns recent runs with dates and row counts, so you can confirm last night's job landed without logging in.

When something goes wrong

You seeWhat it meansWhat to do
401The key is missing, mistyped, or wrongCheck the Authorization header, then ask Jeff for a new key
403The key was cancelledAsk Jeff to issue a new one
413Over 5 MB, or more than 10,000 recordsNarrow the export, or send in batches
415Wrong Content-TypeUse application/json or text/csv
422A required field is missing, or no record was usableRead the error text; nothing was written
429Too many calls in one hourWait. The limit is 10 real runs an hour, and 50 dry runs
Your data is never left half-updated. If a request is rejected — a missing field, or no usable records — the portal writes nothing and your existing data stays exactly as it was. A broken export can't wipe your office.
